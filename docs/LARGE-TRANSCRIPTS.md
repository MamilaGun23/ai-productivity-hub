# Large transcript processing

The meeting workspace accepts pasted text and `.txt`, `.md`, `.vtt`, `.docx`, and text-based `.pdf` files up to 25 MiB. Extraction happens in the browser using [Mammoth](https://github.com/mwilliamson/mammoth.js) raw-text extraction and [PDF.js](https://mozilla.github.io/pdf.js/examples/). Original files are never uploaded. OCR is not included: an image-only PDF is rejected with an actionable explanation, and a mixed PDF warns about pages without text. Corrupt/password-protected documents and DOCX expansion beyond safe bounds are rejected.

Text is normalized without removing speaker labels or timestamps. Chunking uses a conservative UTF-8 byte-token bound, a 32,768-token default context, 8,192 reserved output tokens, and 3,000 prompt overhead tokens. The default section is capped at 14,000 UTF-8 bytes; Unicode characters are never split. Turns are kept intact when possible; unusually long turns are split without dropping any text. A small previous-section overlap supplies reference context. Every original character belongs to exactly one primary section. The context can be changed through `createTranscriptJob`'s `contextTokens` option when configuring another model; do not increase it without verifying that model's supported context.

The browser orchestrates bounded `/api/transcripts/step` requests through map, recursively grouped reduction, and final-report stages. Section notes, actions, and source text remain available for export. Actions are merged by description, owner, and deadline so overlap does not duplicate tasks. Every successful map/reduction node is checkpointed before the next request. The server has no in-memory queue and each request remains below the app's 65,000-byte body cap. Provider JSON is validated on every step. Transient transport/5xx errors receive at most two retries with exponential backoff and jitter; quota/auth/validation errors are never retried blindly.

Jobs and sources use the separate `aph-transcripts` IndexedDB database. Source text is stored once, not in localStorage or the normal saved-output history. A storage adapter interface allows a future durable server implementation. Browser tab locks prevent duplicate execution in supporting browsers. Cancel stops the current fetch, preserves completed sections, and exposes resume. Reloading or closing the tab stops foreground execution; reopening the meeting workspace allows the user to resume. **This is resumable foreground work, not an unattended cloud background service.** Storage is local to this browser and is not cloud synchronized.

The public deployment's shared rate allowance remains 10 requests per 10 minutes. Each section, reduction, and final report uses one request. A very large transcript can require many allowance windows; the UI shows the actual number of sections and preserves a `Retry-After` checkpoint on 429. It does not promise a completion time or bypass public rate controls. An institutional deployment with frequent multi-megabyte transcripts should provision a durable worker/service and explicitly budget a higher managed allowance. The 25 MiB target describes file/extraction support and resumability, not instantaneous hosted generation.

Routine verification uses deterministic SDK mocks and fake IndexedDB. Tests cover exact 25 MiB text preservation, Unicode/turn boundaries, recursive reduction, duplicate-action removal, cancellation/resume without regenerating completed sections, rate cooldown, individual/all-data deletion, invalid documents, and bounded server requests. They do not make paid provider calls.
